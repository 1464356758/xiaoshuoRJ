# 整章单次请求与五审上限（安卓0.15.0 / 云端0.14.0）

按2026-10-19用户的新指令修改。新规则取代本书旧的分段写作、额外付费总监、最多三轮返修及两轮无进步即停规则。旧流程只为已明确绑定singleCallProtocol=0的历史备份保留兼容；新建作品固定启用singleCallProtocol=1，已有V2作品缺字段时在本人下次明确启动时接续新规则，不丢原稿，不重置审核次数。

## 每个环节发几次模型请求

| 环节 | 请求数 | 说明 |
| --- | ---: | --- |
| 全书骨架 / 每批滚动详纲 | 各1 | 独立策划环节，单独列账；不是正文请求 |
| 新章剧情任务书 | 1 | 多个场景是本章结构，不是多次正文请求 |
| 完整一章正文 | 1 | 一次返回全章，不分段、不自动续写 |
| 一次全文审核 | 1 | 所有维度、证据和修改任务验收在这次完成 |
| 总监整理返修指令 | 0 | 直接使用已存真实审稿意见；保存问题ID、定位、改写行动与验收条件 |
| 一轮整章返修 | 1 | 返回完整修改稿，保留旧版，再进行1次全文复审 |
| 自动三章 / 十章联合审核 | 0 | 正文推进不再偷偷增加这些请求；手动独立验收另列 |
| 刷新、查进度、保存设置、手动改稿 | 0 | 仅访问本人服务器；保存本身不启动模型 |

正常新章为任务书1＋正文1＋审核1，共3次；一直返修到第五审为任务书1＋正文1＋返修4＋审核5，共11次。全书策划另计。不是点击开始就只收1次费用，也不保证一定执行满11次：正常通过会提前结束，预算/限流/接口错误会停下。

## 五审后的含义

前四次完整审核未合格时，按真实缺陷继续返修。第5次完整审核后，无论是否85分，允许推进后续章节。正常合格仍要求85及全部关键门；低分或关键问题未关闭则保存needsPolish=true、release.reason=five_reviews、actualQualityPass=false，内部锁住该版本防止覆盖，并在界面和TXT注明“按五审上限放行·待人工精修”。原分数、原文问题及修订历史不改，不等于平台投稿通过。

reviewCount计算已保存且格式/真实证据完整的正式审核，不是attempt返修次数；旧稿按已有有效版本和当前稿去重接续。暂停、重开、换修订nonce、手动保存均不清零。已有五次有效审核的旧阻塞稿，在本人明确继续时使用已存结果放行，不买第六次。畸形JSON、截断、错误证据或超时不算完成审核，停止并保留候选，不循环花钱修复响应。

reviewAttempts同时限制当前协议最多5次实际审核尝试。每个写作/返修/审核/任务书/策划阶段先持久保存请求回执；相同阶段已发出、结果未知或服务器重启，不重放。只有明确在HTTP前被预算等条件挡下，才标记not_sent；本人处理问题并重新启动后，允许发出原阶段的第一次实际请求。免费复用已保存完整候选仍走证据和上下文校验。

严格审稿增加逐场因果、人物信息边界、代价、阅读回报、对白区分、重复解释和结尾核对，要求fix写清场景、具体删改/增补和可观察改善。总监优先整理有具体改法的严重问题，再处理扣分维度；写手不能自评，复审逐项引用新正文说明是否关闭。更清楚的指令有助于改进，但不能保证真实文学分数必然上涨。

五审放行仅携带原文支持且from与已有事实相符的变化进入后文；冲突的变化仍留在原审核和待精修意见中，不覆盖账本。投稿准备仍检查真实质量通过，不能把低分放行冒充合格。备份恢复保留五审记录、实际分数及对应历史正文，不能清洗成PASS。
