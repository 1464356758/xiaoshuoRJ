九、每一步请求次数：必须可证明

严格定义：一个业务步骤最多主动发出1次模型生成HTTP请求。

初稿写作：1次。
每次全文审核：1次。
每轮返修：1次。
总监整理已有意见：0次。
保存设置、保存正文、刷新进度、轮询、健康检查、读取审核、导出：0次。
全书策划与滚动规划：各自独立步骤，每步1次，界面和账目单列。

一章不返修通常为正文1＋审核1，共2次，另加实际发生的规划步骤。达到五审上限最多为正文1＋返修4＋审核5，共10次，规划另列。不自动增加前三章、十章联合审核、文风对比、润色、再总结、自动连接测试等额外请求。

“一次请求”指真实的供应商生成请求，不是App上只显示一条任务。SDK自动重试、网络库重试、代理重试、流断开重接、失败换模型、JSON修补模型、补写结尾，都属于额外请求，默认禁止。

同一个业务步骤的身份必须稳定并持久保存，绑定书、章、输入版本、阶段和任务。刷新、双击、换nonce、手机重连、进程重启和重复启动不得绕过唯一约束。不能因为生成了新任务UUID，就把重复调用洗成新任务。

十、外部API无法与本地数据库做一次原子事务，要正确处理

不得宣称仅凭数据库唯一键，就能保证供应商只扣费一次。V2应实现保守的最多一次主动发送及未知结果停机核对。

模型请求前，先用数据库事务确认：任务仍运行、运行代次有效、没有同业务步骤已发送记录、当前授权有效、没有被其他执行器领取。持久记录发送意图后才发HTTP。

供应商请求结束后，保存原始响应、HTTP状态、供应商请求ID（如果返回）、usage、输入输出版本及阶段结果，再推进下一阶段。私人响应不能进公开日志。

以下情况一律不自动重发：超时、流中断、进程退出、HTTP错误、坏JSON、供应商已接收但本地没拿到结果、已经拿到结果却尚未保存业务稿。

如果发送意图已记录但无法证明HTTP到底有没有发出，视为可能已发送，不自动补发。这样可能少执行一次，但不会用不确定性启动一串收费请求。

已保存的付费响应允许本地重新解析和确定性校验，不再次调用模型，不伪造内容、引文或供应商用量。无法恢复的结果保留“待核对”。如本人以后明确选择另开一次请求，应单独显示其额外调用性质，不能由“继续”静默触发。

十一、停止必须对应真实运行状态

1. “停止任务”先持久阻止后续调用，再取消当前HTTP等待，并使旧执行器失去继续推进的权限。可使用运行代次、租约及事务核对实现。
2. 所有模型入口共用同一停止检查和调用出口，包括策划、写作、返修、审核、连接测试和可选文风分析。
3. 界面区分“正在停止”“已停止”“在途结果待核对”。不能任务仍有权发请求，却显示已经停止。
4. 已被供应商接收的请求，取消后仍可能执行或计费，必须据实记录。无法从客户端保证撤销供应商已经开始的计算，不得承诺按停止就绝对零费用。
5. 停止后等待任意数量的状态轮询都不能产生新模型请求。App退出不等于按停止。
6. 服务器重启后保持用户的停止状态；没有明确启动，不恢复旧任务。可确认未发送且仍运行的排队步骤，才能按原任务恢复。
7. 使用一个有效执行器和有期限的租约，处理租约过期和旧执行器迟到写入。不要通过增加worker数量掩盖调度问题。
8. 保留简单共享频率限制，优先沿用既有合理数量级，例如所有角色合计每分钟6次、每小时60次。达到频率限制时显示下一次可运行时间，不不断尝试预留或请求。频率门不冒充金额门。

十二、审核必须给出可执行问题，不是反复打一个数字

评分量尺在同一本书内保持一致，建议：商业钩子20、因果逻辑20、人物选择20、节奏15、语言15、原创性10，总分100。

每份审核必须绑定本章正文hash，并保存：
- 六个维度的真实分数、上限、扣分理由和正文依据；
- 总分，由程序按六项求和，校验范围，不偷偷改分或保底；
- 问题ID、位置、严重程度、为什么影响阅读；
- 一条确定的修改办法及验收条件；
- 本次实际完成的事实或人物状态变化，以及待核实项。

问题描述必须可执行。不要只写“人物不够立体”“节奏一般”“文笔有待提升”。例如，应说明“某人在第几段直接答应冒险，却没有其自身利益或风险权衡；在现有谈判中增加一个明确条件和一次选择，保持本章终点不变”。

对本来已经成立的内容，不能要求当作缺失项重复补一遍。重大问题与普通润色分开，不让标点或小格式错误变成阻塞整本书的理由。

审核可以连续给出78分，前提是依据真实；不能为了看起来修好了硬凑85分。界面要展示维度增减和问题状态，让人知道“改了哪些、为什么总分没变”。

十三、总监下达具体返修任务，写手按任务改

总监直接消费上一份有效审核，不另买一轮模型总结。

每轮选择有限、真实、优先级最高的问题，生成任务：问题ID、原文位置、具体改法、必须保留的事实和结尾、验收条件。不要用宽泛的评分赞扬凑任务数量，不把互相矛盾的改法一起交给写手。

默认采用定点返修，保留未涉及正文。建议由服务端为原稿段落分配ID和hash，写手只提交对应段落的替换内容及问题ID。不要把模型必须重新抄对一长段原文定位短句，作为唯一可用的修改入口。

一种可采用的最小协议是：
{
  "baseHash": "原稿版本",
  "edits": [
    {
      "paragraphId": "P012",
      "expectedHash": "该原段落hash",
      "replacement": "修改后的完整段落，可包含必要的新段落",
      "issueIds": ["I-03"]
    }
  ],
  "unresolved": [
    {"issueId": "I-04", "reason": "为什么当前不能安全解决"}
  ]
}

这是供你落实的简化方案，不要求机械照抄字段名，但必须实现等效的原稿绑定、定位唯一、修改范围验证、任务覆盖、版本留存和一次请求。

程序保存实际修改前后、段落位置、问题ID、原稿hash和新稿hash。只改标点、空白、标题或返回原稿，不能算完成实质返修，也不能马上花钱再审同稿。

如果确实属于必须重写全章的结构问题，可以设计一个清楚标识的整章返修模式，同样只有1次请求、保留原稿并限制剧情边界。不得在定点返修失败后偷偷切整章模式再请求。

返修必须保持：人物知识边界、资源数量、信物归属、时间因果、已成立的选择、本章结束位置和下一章才发生的事件。补动机优先替换冗余解释，不靠增加大量新事件扩字数。

十四、复审依据实际差异验收，五审后按规则收稿

复审仍然只请求1次，必须读取修改后的全文，并拿到程序计算的真实修改前后对照。

每项“已解决”必须关联对应问题ID和本轮实际修改位置，给出新稿依据及解释。程序核对其来源和范围，审核模型负责判断语义上是否真的改善；不能把范围校验宣传成机器已证明文学质量提升。

“新稿里有这句话”不足以证明本轮解决了问题。若旧稿本来就有该内容，或证据引用了本轮没改的位置，应显示“该项未通过差异验收”，保留模型原判断、真实分数和问题，不为修一个证据格式另买一次审核。

个别引文或编号无效，尽量降为未核实项，不直接丢弃整份已付费报告。严重缺失、截断或绑定错误则保留响应并停止，不伪造一个完成的审核，也不自动重试。

次数规则是我的硬要求：
1. 审核次数按本章已完成、绑定真实正文的有效全文审核计数。
2. 初审计第1次；后续每次有效复审各加1。
3. 前4次未合格，按具体意见返修；合格可以提前收稿。
4. 第5次有效审核结束后，无论是否达到85分，均按“五审上限收稿／待人工精修”继续后续章节。
5. 分数、问题、审核结论原样保留，不把78写成85，不伪装成模型判定合格。
6. 后续精修属于本人另行明确的编辑任务，不在原生产任务里无限增加第6次、第7次审核。
7. 暂停、重启、换配置、恢复备份或更新App不得把同一章的审核次数清零。
8. 请求失败、返修失败、免费检查和读取历史审核都不计有效审核。

十五、长篇不能中段循环，文风不能全是模板

全书规划应有明确主线、阶段目标、反派策略升级、人物关系变化、阶段兑现和终局方向。

每章任务说明开场处境、主要冲突、人物选择、代价、实际变化、兑现点和结束位置。与过去几章相比，本章必须有推进，不能不断回到相同的调查、受辱、误会、验证或空泛威胁。

维护简短可追溯的长期记忆：人物当前状态与知情范围、承诺与关系、资源与伤势、未兑现线索、已兑现回报、当前时间、已发生事件和不应重复的情节。更新使用同一次审核结果及本地处理，不能每章另加一次付费总结。

正文追求具体动作、有个性的对白、明确利益与代价、自然段落节奏。少用万能比喻、旁白解释、空泛狠话和机械章末钩子。爽点需要铺垫、选择、兑现和后果，不靠人物集体降智。

支持我输入文风要求，或导入本人提供的TXT作为参考，抽取叙述、对白、句式和节奏等方法。不要默认下载别人的整本付费小说，也不要复制现成角色、情节和长段原文。文风分析若需要模型，应是本人明确启动的单独1次任务，不能隐藏在每章流程里。

先完成创作、返修、审核、停止和恢复。多版本文风实验、自动赚钱看板、收入模拟等不列为核心交付前置条件。

十六、手机界面要清楚、按钮要有效
